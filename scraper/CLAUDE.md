Repo-wide conventions live in `../CLAUDE.md`. Before working here, read the
[scraper architecture](../docs/KAN-55_JOB_SCRAPER.md) and its
[research appendix](../docs/KAN-55_SCRAPER_RESEARCH.md). The

"working" means once the implementation exists — its check IDs (`C17`, `F14`,
`H16`) are the reference to cite in PRs and test names.

## Status and boundary

This folder is the Python job-ingestion scaffold. Packaging, HTTPX, development
tool configuration, and module placeholders exist. The CLI, provider adapters,
database store, migrations, seed CSVs, and tests are not implemented yet. Do not
describe the npm scraper forwarders as a working scraper.

Initial providers are Greenhouse, Lever, Ashby, and SmartRecruiters. Adapt the
pinned reference modules and relevant tests rather than importing a whole
scraping platform. Python and `frontend/` meet at Supabase Postgres; neither
imports the other's application code.

## Development commands

Python 3.12+ and [uv](https://docs.astral.sh/uv/) are required — the same
version `backend/` pins, so one interpreter serves both. Run from the
repository root:

```text
uv --directory scraper sync --extra dev         # include optional dev tools
uv --directory scraper run ruff check .         # lint
uv --directory scraper run mypy .               # type-check
uv --directory scraper run pytest               # once tests exist
```

`npm run install:scraper` currently installs runtime dependencies only. Use
the command above for lint/type-check/test tools. Root `scraper:*` scripts
forward these checks through `uv`; installing uv itself is separate.

The future CLI provides `discover`, `poll`, and `reprocess`; no subcommand
defaults to `poll`. The dry-run form is
`poll --dry-run --sources <file>` (or the root forwarder
`npm run scrape:dry -- --sources <file>`). It uses explicit local input and
gitignored `scraper/.scraped/` output without opening a database connection.
These are implementation contracts, not commands available in this scaffold.

## Persistence rules

**v1 does not use the database.** The store is a protocol with two
implementations: `JsonStore` writes gitignored files under `scraper/.scraped/`
and is what v1 ships; `PostgresStore` arrives once KAN-93's schema lands. Both
honour the same contract, so lifecycle and caching are built once. One file per
board, committed by atomic replace — see the architecture §5.

Everything below governs the Postgres implementation when it lands.

**The ingestion migration is written in `backend/`, not here.** The five
tables are SQLAlchemy models in the API project and land in its Alembic
history; this package writes rows through them and owns no revision.

**Alembic owns the schema, in one revision history for the whole database.**
Tables are SQLAlchemy models in the Python backend (KAN-93); `frontend/` holds
no ORM and no migrations. Add SQLAlchemy when the store lands and share the
backend's engine and model metadata — do not open a second connection layer,
start a second migration chain, or issue ad-hoc DDL, including staging tables.
Two revision histories against one database diverge silently.

Autogenerated Alembic revisions are a draft, not a result: review the emitted
DDL before committing, because autogenerate does not reliably detect
constraint or index changes. Migrations run over the session pooler (5432);
DDL and migration locks need a session-scoped connection.

KAN-50's company schema is a dependency; its design is on the
`KAN-50-login-business-profiles` branch and its tables are not implemented in
this checkout. It arrives as SQLAlchemy models in KAN-93, and its revision must
precede any ingestion revision carrying company foreign keys. Do not create a
competing company model here.

Postgres is authoritative. Ingestion is service-only; public job reads require
`active AND is_listed`. Payload and operational tables are not public. Sources
and scraped jobs may have a null company mapping; discovery cannot create
memberships or mark a company claimed. Preserve employer-authored rows and
stable job IDs. Disabling a source does not delete its jobs.

Fetch outside a write transaction. Commit each board's jobs, payloads,
lifecycle, outcome, and checkpoint together under a source row lock and
version comparison. A failed write must not advance its ETag. Conflicting or
repeated observations must not increment missing streaks again.

## Adapter and lifecycle rules

- `FetchResult` separates listing completeness, observed IDs, usable content,
  and detail failures. Lever uses an array envelope; the other initial
  providers use object envelopes. Invalid identities and pagination failures
  make enumeration incomplete. A valid ID still supplies presence when its
  content cannot be normalized.
- Every positive observation resets missing streaks and reopens the same job
  row, even when the content hash is unchanged. Close on two distinct accepted
  complete absences since the last positive observation, with sweeping enabled.
  Failed, partial, skipped, and 304 results supply no negative evidence.
- SmartRecruiters must enumerate all pages. The reference scraper's 300-job
  cap is not a provider ceiling. Local safety limits produce partial results.
- Conditional requests are limited to eligible whole-list representations.
  Pending misses, rejected content, failed details, or due refreshes require a
  body response. A 304 records source validation, not a new job observation.
- Keep latest full listing/detail replay material privately. Failed details
  retain prior successful content and remain pending. Versioned reprocessing
  corrects content independently of polling without changing lifecycle.
- Preserve structured salary tiers, all locations, timestamp provenance, and
  unknown values. Do not manufacture salary units or remote status. Treat
  source HTML as untrusted content.

Provider-level anomaly alerts are operational signals, not per-board sweep
gates. Limits, retries, breaker behavior, and rollout criteria are specified in
the architecture; do not treat reference defaults as provider entitlements.

## Fixtures and attribution

Real scraped postings and captured responses never enter Git. Commit only
synthetic or sanitized structural fixtures with invented text and identities.
Default tests are offline; live probes are opt-in and their output stays
gitignored. The architecture's acceptance table is the implementation test
plan; dry runs do not verify database lifecycle behavior.

Keep [THIRD_PARTY.md](workit_scraper/THIRD_PARTY.md) with adapted code/data.
Update its copied-path inventory when implementation or seed imports actually
land. It currently records design references and planned adaptations.
