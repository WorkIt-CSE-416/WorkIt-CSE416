# Repairs: Claude Code fixes Apply's code, gated in plain code

When an Application fails for a reason of Apply's own making (an error, a question the planner missed, a field a Filler misfilled), Apply keeps a Repair request and later runs `claude -p` (Sonnet, on the Max login) in a fresh git worktree to fix it test-first, the loop we ran by hand on every rehearsal batch. Filling now lives in the Fill engine (ADR 0004), so the worktree's `autofiller_extension/fill-engine` is a worktree of the fill-engine repo on a branch of the same name, from the commit Apply pins: a fix to a Filler or a rule is written there, with the engine's own tests. Claude gets file tools that edit only Apply's code, tests and docs and the engine's `src/`, `test/` and `dist/` (never a protected path or a conftest.py), and only `uv run pytest`, the engine's `npm test` and `npm run build`, and read-and-commit git commands in either repo; it can't push, merge, run Apply or open a browser.

Whether the fix lands is decided by plain code, not by Claude: no commit may touch a protected path, no test file may lose a test or an assertion, no saved form may change, and both suites must pass. The protected paths, in their places since the engine moved out:

- **In Apply (`apply-agent/`)**: everything that decides or sends a submit, which all stays in Apply: the submit guard, the Orchestrator and Worker that decide submit or hold, the Pre-submit check, each Filler's `submit` and what it uses (its Python module keeps it: greenhouse.py, lever.py, ashby.py, workday.py, rippling.py, workable.py, eightfold.py), Claude fill's submit, drive guard and sign-in, and the wait for a job system's confirmation; the Emailed code typed after Lisul's own submit (email_code.py, with its test); eligibility and essays; the browsers, sign-in, Gmail and Keychain; the Applicant profile, the Answer bank, the Story bank, policies.yaml; the dependencies; the Repair code itself; and any conftest.py or pytest config, which the Repair's own test runs would execute. The pointer to the engine (`autofiller_extension/fill-engine`) is moved only by the Repairer, never by Claude's commits.
- **In the engine (`autofiller_extension/fill-engine`)**: its dependencies (`package.json`, `package-lock.json`), and what `npm test` runs before any test (`playwright.config.ts`, its globalSetup `test/build.ts`, `tsconfig.json`); anything outside `src/`, `test/` and `dist/`; a saved form in `test/fixtures/` (new ones may be added); the Hold rules (`src/holds.ts`, moved there from Apply's holds.py); and a test or an assertion lost from a `*.spec.ts`. The engine never submits: a Repair that adds a call to `submit(` or `requestSubmit(` in `src/` waits for Lisul, and on Apply's pages the submit guard still blocks any submit a fill would make.

The engine's tests (`npm test`, which rebuilds `dist/engine.js`) must pass and leave the committed bundle unchanged, since Apply runs the committed bundle; then Apply's whole suite must pass against the changed engine. Only then are the engine commits merged into the branch Apply's submodule tracks (`branch` in `.gitmodules`: main) and pushed, Apply's pointer moved to them in a commit of its own, and the Apply branch merged into the integration branch and pushed; the checkout Apply runs from updates its submodule, so the next run uses the fixed engine. If either branch moved meanwhile, it is merged in and both suites run again. Anything else waits on its branches (`repair/<signature>` in both repos) for Lisul, who gets a notification. WorkIt pins its own engine version, which a Repair never moves: WorkIt takes an engine fix only when someone moves its pin.

## Consequences

- A Repair can change how forms are filled without Lisul reading it first. The gate keeps it from changing whether an Application is submitted, and the Calibration run and Hold rules still apply to every Application it requeues.
- One cause makes one Repair request (a signature of the error's type, its innermost Apply frame and its message shape, or a question's normalized wording), and at most `repair.max_per_day` Repairs run a day, so a bad night costs a bounded share of Lisul's Max usage.
- A Missing fact that no profile entry answers is not Apply's bug: the Repair says so, commits nothing, and the question stays Lisul's to answer.
