# Bot-protected job forms without evading detection

**Status (2026-11-05):** The vendor and market findings stand. The recommendation below (hand off to the everyday Chrome) was not built. Plain Workers replaced it: see [everyday-chrome-fill-design.md](everyday-chrome-fill-design.md).

Researched 2026-11-04. The question: how can Apply work on forms behind Cloudflare (Workable), DataDome (SmartRecruiters) and hCaptcha (Lever) with no stealth, spoofing, patched browsers, solvers or proxies? This builds on [datadome-smartrecruiters.md](datadome-smartrecruiters.md), which already covers the Simplify, Jobright and LazyApply bundles, AIHawk, Massive, DataDome's CDP signal and `--remote-debugging-port=0`. That material is not repeated here. Read-only checks only: two `curl` GETs of public form pages, a read of the Chromium string table and of `cloudflare/web-bot-auth`. No form was filled or sent.

## Summary

1. All three vendors say the same thing: automation frameworks are not a supported way to pass a production challenge. Their sanctioned path for automation is to **declare** it (Cloudflare Web Bot Auth or signed agents, DataDome Bot Authentication). The site owner then decides whether to let it in. Both programs are built for agent operators serving many users, not one person's assistant.
2. The products that work on these sites all run **in the user's own browser**, either as an extension (Simplify, Jobright, Claude in Chrome, the ChatGPT extension that replaced Atlas) or as the browser itself (Comet, Chrome auto browse). On a captcha, every one of them pauses and the human solves it. None documents a way through.
3. An MV3 content script in the user's everyday Chrome leaves none of the automation markers the vendors name: no CDP, no webdriver flag, no automation switches. Its synthetic events do carry `isTrusted=false`. That matters less than it sounds, because no vendor documents checking form-field events, and the user's own scrolling, clicking and the Submit press are real input. It is still unverified live.
4. `chrome.debugger` is a CDP client. It raises a permanent "started debugging this browser" infobar and is the exact layer detection vendors fingerprint. Chrome's own agent (Gemini auto browse) is consumer-only and has no developer API. WebMCP is a site-side API still in early preview.
5. **Recommendation:** on any bot wall, Apply hands the posting to the user's everyday Chrome and the WorkIt extension fills it there. The user solves any challenge in that same tab and presses Submit. Apply's Worker Chrome never asks them to solve a challenge, because Cloudflare says challenges are unsupported in automated browsers.

## 1. What the vendors document

### Cloudflare (Workable)

- **The Workable page.** A plain GET of one public `apply.workable.com` form returned `server: cloudflare` and set a `__cf_bm` cookie (Cloudflare bot management). The HTML references `turnstile` twice and `recaptcha` once. So Workable runs both a bot-management layer and a Turnstile widget on the form.
- **Automated browsers are unsupported.** The [Supported browsers](https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/) page (updated 2026-08-18) says: "Automated browsers are not supported for solving production challenges." It also says: "Browser automation frameworks, such as Selenium, Puppeteer, Playwright, and Cypress, are not supported for solving production challenges. For automated Turnstile testing, use Turnstile test keys." This covers Apply's Playwright Worker even when a human does the clicking.
- **Extensions are a known nuisance, not a block.** The same page names "Ad blockers and content blockers", "fingerprinting protection, or canvas blockers" and "VPN or proxy extensions" as causes of failure. It does not name form-filling extensions. Its advice is: "If challenges consistently fail, try temporarily disabling extensions and reload the page."
- **Clearance stays on one device.** "The cookie is securely tied to the specific visitor and device it was issued to, preventing reuse across machines." Clearance lasts as long as the site owner configures, "unless Precursor in Armed mode determines the session is suspicious", in which case "The visitor may be re-challenged, even if the cookie has not expired." ([Clearance](https://developers.cloudflare.com/cloudflare-challenges/concepts/clearance/), 2026-10-23.) A solve done in one browser does not carry over to another. Copying the cookie over would defeat the control the cookie exists for.
- **Verified bots and signed agents.** Since 2026-07-01, signed agents are folded into Verified bots. A Verified bot must meet two bars: "Honest self-identification" (via "a cryptographic Web Bot Auth signature, a published IP list with a stable user-agent, or reverse DNS") and "Non-abusive behavior". One listed behavior is "Agent: User-directed agents visiting a page on behalf of a human." Operators are labelled "Direct" ("Operated by a single, narrow operator") or "Intermediary" ("An agentic service that a wide range of end users can operate"). Approval goes through the BotBase form, and on rejection "The dashboard does not show the rejection reason." ([Verified bots](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/), 2026-11-02.)
- **Signed agents were designed for platforms.** The launch post describes them as "agents that are generally directed by an end user instead of a single company or entity". It names a first cohort of "ChatGPT agent, Goose from Block, Browserbase, and Anchor Browser". ([Cloudflare blog, 2025-08-28](https://blog.cloudflare.com/signed-agents/).) OpenAI's cloud browser "uses Web Bot Auth to sign outbound HTTP requests" with `Signature-Agent: "https://chatgpt.com"`. OpenAI tells site owners to allow it with Cloudflare detection ID 129220581, which means that being signed is not the same as being allowed ([OpenAI help](https://help.openai.com/en/articles/11845367)).
- **Web Bot Auth mechanics.** You generate an Ed25519 key and host a signed JWKS at `/.well-known/http-message-signatures-directory`. You register it through the Bot Submission Form, then attach `Signature`, `Signature-Input` and `Signature-Agent` to every request ([Web Bot Auth docs](https://developers.cloudflare.com/bots/reference/bot-verification/web-bot-auth/), 2026-10-08). Cloudflare Research's [reference browser extension](https://github.com/cloudflare/web-bot-auth/tree/main/examples/browser-extension) signs every outgoing request. Per its README, it "requires the webRequestBlocking permission, which in turn requires of an Enterprise policy to be configured on Chrome."
- **The site owner decides.** "All customers have the option to configure AI Crawler and Agent access policies to define their block vs. allow expectations" ([Verified bots](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/), Availability). If the operator uses plain Bot Fight Mode, "You cannot bypass or skip Bot Fight Mode using WAF custom rules" ([Bot Fight Mode](https://developers.cloudflare.com/bots/get-started/bot-fight-mode/)). Even a site that wanted to make an exception could not do it there.

**Does any of this fit one person's agent?** Only in theory. Nothing excludes a "Direct" single-operator bot, but approval is discretionary. A signature also *announces* a bot, and Workable, as the operator, can then block the Agent category. A signature does not answer a Turnstile widget either: Turnstile is client-side and scores the browser itself. Web Bot Auth helps a known agent that site owners choose to allow. It does not help an unknown personal agent past a form the owner chose to guard.

### DataDome (SmartRecruiters)

The earlier note covers its signals and its [Bot Authentication](https://docs.datadome.co/docs/bot-authentication) path, where "our customers can decide to authorize them". The new item is [Agentic Trust](https://docs.datadome.co/docs/agentic-trust-getting-started). It identifies agents by "Web Bot Authentication" and KYA (Know Your Agent), plus IP lists and reverse DNS. Agents without those are handled by "behavioral and technical fingerprinting". The customer has "total control over how every AI agent interacts with your platform." SmartRecruiters deployed DataDome on application flows specifically to stop "automated submissions" (case study in the earlier note). DataDome's page does not address agents that run inside a user's browser.

### hCaptcha (Lever)

- **The Lever page.** A GET of a Lever `/apply` page shows `h-captcha`, `data-sitekey`, `hcaptcha.render` and `hcaptcha.execute`. Like the earlier note says, it is invisible hCaptcha, run when Submit is pressed.
- **Invisible mode.** The [developer guide](https://docs.hcaptcha.com/) renders an invisible widget and calls `hcaptcha.execute(widgetId)` in the submit handler ("Trigger the hCaptcha flow programmatically"). Whether a picture challenge appears "depends on computed confidence in the visitor's humanity, the site difficulty setting, and other security factors" ([FAQ](https://docs.hcaptcha.com/faq)). That setting belongs to the site operator.
- **Test keys are for tests only.** "The test keys provide no anti-bot protection, so please double-check that you use them only in your test environment!" They are not a path for production.
- **Accessibility is not an agent path.** hCaptcha's [accessibility page](https://www.hcaptcha.com/learning/accessibility/hcaptcha-accessibility/) offers a text challenge, when the site enables it, and a registration cookie for users with impairments. Using either for an agent would misuse an accommodation. One user [reports being banned](https://engineered.at/articles/i-was-banned-from-the-hcaptcha-accessibility-account-for-not-being-blind) from the programme for not being blind. Ruled out.

## 3. Does an MV3 content-script extension pass?

What the vendors name as automation: CDP clients, `navigator.webdriver`, automation frameworks, headless mode, emulation overrides, VPN/proxy and fingerprint blockers. A content script uses none of these. It runs in an isolated world "that isn't accessible to the page" ([Chrome docs](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)), in the user's own profile, IP, cookies and history.

What it does leave:

- **Untrusted events.** `isTrusted` "is `true` when the event was generated by the user agent ... and `false` when the event was dispatched via `EventTarget.dispatchEvent()`. The `click` event fired through `HTMLElement.click()` sets the `isTrusted` property to `false`" ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Event/isTrusted)). The `input` and `change` events a filler dispatches therefore read `false`. Assigning `.value` fires nothing at all. `element.focus()` does produce trusted focus events.
- **What vendors watch.** DataDome's tag collects "behavioral data ... such as mouse movements or key strokes" (earlier note). Turnstile lists "probing for web APIs" and "detecting browser-quirks and human behavior" ([Turnstile FAQ](https://developers.cloudflare.com/turnstile/frequently-asked-questions/)). Neither says it scores untrusted events on form fields. Both score the session. In the hand-off flow the session is a real person: The user opens the tab, scrolls, checks the fields, and their own Submit click is trusted. That click is also the moment invisible hCaptcha runs.
- **Extension presence.** Pages can detect a specific extension through its web-accessible resources and DOM artifacts. CHEQ shows this for Claude in Chrome (`claude-agent-stop-container`). That identifies the tool, not a bot, and Simplify and Jobright have the same exposure. WorkIt's extension should still avoid exposing web-accessible resources and leave no DOM markers it does not need.
- **Evidence it works.** Simplify, Jobright and WorkIt fill SmartRecruiters, Lever and Workable-type forms this way. No vendor or product says it gets challenged for it. **Not tested live for Apply.** That remains the open check from the earlier note.

Verdict: likely treated as a normal user for all three. The residual risk is behavioral: a page filled in milliseconds with no human present. A human-present flow removes that risk. Artificial pacing does not, and adding it would edge toward imitation.

## 4. Chrome-native options

- **`chrome.debugger`** is "an alternate transport for Chrome's remote debugging protocol" ([Chrome docs](https://developer.chrome.com/docs/extensions/reference/api/debugger)). Chrome shows the infobar `"<extension>" started debugging this browser`. Chromium's string table says it "does not disappear until the user dismisses it, even if the debugger is detached" (`IDS_DEV_TOOLS_INFOBAR_LABEL`, [generated_resources.grd](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/app/generated_resources.grd)). It does not set the webdriver flag, which comes from launch switches. But it *is* CDP, the layer DataDome targets, and its `Input.dispatch*` events are trusted. CHEQ describes them as "indistinguishable from human hardware input". Using trusted synthetic input to get past a check that looks for human input is the evasion this project rules out, so it should never touch a challenge widget. Its one honest use is the rare widget a content script cannot drive, with the user watching. Even then, Claude in Chrome pauses at captchas.
- **Gemini in Chrome auto browse** is a consumer feature: "Be 18 or over and in the US", "Google AI Pro or Ultra", desktop, gradual rollout. Google documents no developer API, and it asks before submitting forms ([Chrome Help](https://support.google.com/chrome/answer/16821166)). Apply cannot call it. The user could use it by hand, but that is a separate product.
- **WebMCP** (`navigator.modelContext`) lets a *site* expose tools to an agent. It was in early preview in Chrome 146 Canary behind a flag ([eWeek](https://www.eweek.com/de/news/google-webmcp-chrome-ai-web-standard-preview/), secondary). It helps only if Workable, SmartRecruiters or Lever adopt it. That is worth watching, but it does nothing today.
- **Chrome's built-in AI APIs** (Prompt API and others) are on-device models, not browser control. They don't apply here.

## 5. Human-in-the-loop that actually clears

- **Solve where you fill.** Clearance is "tied to the specific visitor and device". Challenges are "not supported" in automated browsers. So a challenge must be solved in the same non-automated Chrome that sends the form. Apply's current Handoff brings the *Worker's* window forward for "a sign-in, a captcha, a dialog" (`dashboard.py`). On Cloudflare that can loop or fail, because the Worker is Playwright-launched with `--remote-debugging-port=0`.
- **The flow that works.** Apply detects the wall and makes a Handoff. It opens the URL in the user's everyday Chrome with `open -a "Google Chrome" <url>`, which uses no CDP. The WorkIt extension fills the form. The user solves anything that appears and presses Submit. Every vendor allows this, and every competitor does it.
- **Session continuity.** Once the user passes a Workable Turnstile or managed challenge in their Chrome, their `cf_clearance` covers later Workable pages for the window the site configured. Later Workable applications in that same Chrome may go through without a challenge. Precursor may still re-challenge.
- **Don't retry automatically.** This follows DataDome's "Do not retry automatically" (earlier note). It also protects the shared network's IP reputation.

## Recommendation

Adopt **B** as the standard path for any Application that meets a bot wall, and stop asking the user to solve challenges in Worker Chrome.

1. **Detect early and stop.** Before or at the first fill, extend `bot_signals.py` to recognize the walls: the Cloudflare interstitial (`#challenge-stage`, "Just a moment"), a Turnstile iframe from `challenges.cloudflare.com`, DataDome (`captcha-delivery.com`, a `datadome` cookie) and an hCaptcha challenge frame. On any of these, close the Worker page and make a Handoff with reason "bot protection". Don't retry.
2. **Hand off to real Chrome.** The Handoff button runs `open -a "Google Chrome" <url>`, with no CDP and no `--remote-debugging-port`. The WorkIt extension fills from the same profile and answers (native messaging is already mapped in [apply-sign-in-options.md](apply-sign-in-options.md) option 2). The user solves whatever appears and presses Submit. The extension reports the confirmation back so the tracker row closes.
3. **Learn per host.** Remember which hosts walled (Workable, SmartRecruiters). Send their future Applications straight to the hand-off instead of trying a Worker first. That costs nothing and stops repeat hits on the shared network's IP.
4. **Keep the extension clean:** no `debugger` permission, minimal web-accessible resources, no DOM markers beyond its own UI. Never touch challenge iframes (Simplify's `urlsExcluded` pattern).
5. **Skip Web Bot Auth for now.** It declares a bot to operators who chose to block automated submissions, needs discretionary approval, and does not answer Turnstile. Revisit only if Workable, SmartRecruiters or Lever publish an allow policy for signed agents, or adopt WebMCP.

**What it costs:** these hosts lose unattended, parallel filling. Each needs the user at the keyboard for about the length of their review, which they already does before every submit.
