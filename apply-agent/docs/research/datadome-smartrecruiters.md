# How do other tools get past DataDome on SmartRecruiters?

**Status (2026-11-05):** The findings stand. The recommendation (hand off to the everyday Chrome) was not built. Plain Workers replaced it: see [everyday-chrome-fill-design.md](everyday-chrome-fill-design.md).

Researched 2026-11-03. The trigger was a SmartRecruiters form that showed Apply DataDome's "We detected unusual activity from your device or network" page. For this note I downloaded three extensions again from the Chrome Web Store's update endpoint: Simplify 3.1.13, Jobright 1.25.2 and LazyApply 0.8.95. I unpacked them into the scratchpad and only grepped them; nothing was loaded or run. Scope: what other tools do, and what stays within the rules. No stealth, spoofing or solving work was done.

## Short answer

None of them gets past DataDome. The tools that work on SmartRecruiters run as an **extension in the user's own Chrome**, with the user's cookies and IP. When a challenge appears, the user solves it. Cloud services don't say how they handle it. Only one open-source project, the former AIHawk, now advertises being "undetectable by anti-bot systems", and that is the stealth route this note rules out.

**Recommendation.** When Apply gets a DataDome page, it should stop, make the Application a Handoff and open the posting in the user's everyday Chrome with a plain `open -a "Google Chrome" <url>`, not over CDP. The WorkIt extension, which already matches `jobs.smartrecruiters.com`, fills the form there. The user solves any challenge and presses Submit himself. Apply should not retry on its own.

## 2. What they do at a DataDome page or captcha

- **No bundle mentions DataDome.** I grepped all three for `datadome`, `captcha-delivery` and "unusual activity" and found nothing. None of them special-cases it.
- **Simplify:** it keeps its panel off captcha frames (`render.urlsExcluded`: `*.google.com/recaptcha/*`, `*.recaptcha.net/recaptcha/*`, `*.hcaptcha.com/captcha/*`). It has no solving code. The user handles the challenge.
- **Jobright:** it detects Cloudflare challenge pages (`#challenge-stage`, `#cf-challenge-running`, `.cf-browser-verification`, "performance and security by cloudflare") so it can stop. It has no solving code.
- **LazyApply:** it shows "⚠️ Captcha Detected - Waiting for it to be solved" and waits (`atsAutomation.bundle.js`). Users report it "couldn't get past Indeed captcha" ([Scoutify](https://scoutify.com/blog/lazyapply-review), secondary). Its [terms](https://lazyapply.com/terms) (January 2024) leave third-party sites "entirely at your own risk".
- **AIHawk successor:** it avoids detection by patching the browser engine instead of handing off. Its README tells users to "respect the terms of the sites it visits". The older AIHawk disclaimer says "the use of automated tools for job applications may have implications on user accounts".
- **Massive and Sonara:** no public statement. One competitor blog claims Massive gives generic results; it is not evidence.
- **Who uses solving services:** none of the products read here. Solver extensions do exist on the Chrome Web Store, such as "Auto CAPTCHA with LLM", but no job tool was seen bundling one.

So the market pattern is **detect, then wait for the human or hand off**. The only alternative on the market is engine-level stealth.

## 3. Why DataDome flags CDP-driven Chrome but not an extension

From DataDome's own documentation and research:

- **The JavaScript tag** collects "behavioral data ... such as mouse movements or key strokes" and "generic information ... about the OS, the browser itself, the GPU". It also runs consistency checks on built-in browser functions meant to catch headless Chrome, Puppeteer and Selenium. Detection runs in DataDome's engine, not on the page. ([JavaScript Tag docs](https://docs.datadome.co/docs/javascript-tag))
- **Device Check** looks for "automation frameworks, spoofed environments, or programmatic access" using screen, codecs, plugins, CPU/GPU and JS timing challenges. ([Device Check docs](https://docs.datadome.co/docs/device-check))
- **The CDP signal.** DataDome's research says "the main bot frameworks—such as Puppeteer, Playwright, and Selenium" drive Chrome over CDP. Its detection exploits the serialization that happens once a client has sent `Runtime.enable`, and "CDP detection is efficient both for Chrome and Headless Chrome". It is layered with behavior, "IP and session reputation" and consistency between IP location, time zone and language. ([Vastel, DataDome, 2024-06-13, syndicated](https://securityboulevard.com/2024/06/how-new-headless-chrome-the-cdp-signal-are-impacting-bot-detection); datadome.co returns 403 to fetchers.) Two V8 commits from May 2025 broke that particular `Error.stack` trick ([Castle](https://blog.castle.io/why-a-classic-cdp-bot-detection-signal-suddenly-stopped-working-and-nobody-noticed/)), so DataDome now leans more on the other layers.
- **`navigator.webdriver`.** MDN says that in Chrome it is true when "the `--remote-debugging-port` flag specifying port 0 is used", and also with `--enable-automation` or `--headless` ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/webdriver)). **Apply passes exactly `--remote-debugging-port=0`** (`browsers.py`), so its pages very likely report webdriver as true. That is a declared-automation flag, not a subtle fingerprint. This was not tested live.
- **Other differences in Apply's browser.** Playwright launches Chrome with its own switches: `--disable-extensions`, `--disable-sync`, `--disable-background-networking`, `--use-mock-keychain`, `--password-store=basic` and others (`chromiumSwitches` in Playwright 1.64's `coreBundle.js`). Fills happen with no human mouse or keyboard trail. Worker profiles are copies, not the user's daily profile.
- **Network.** A university network puts many users behind shared IPs. If one of them looks automated, the address's reputation suffers for everyone. Users who see this exact block page say it lists "automated (bot) activity on your network" among the causes ([Mozilla support thread](https://support.mozilla.org/ee/questions/1515746), secondary). DataDome does not say which signal fired, and from outside we can't tell either.

**Why an extension is different.** A content script runs in an "isolated world ... that isn't accessible to the page" ([Chrome docs](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)). It does not use CDP. The browser is the user's normal Chrome with no automation flag, its real history and cookies, and the user's own mouse and keyboard on the page. Nothing in DataDome's signal list points at it. One caveat: an extension that uses `chrome.debugger` *is* a CDP client ("an alternate transport for Chrome's remote debugging protocol", [Chrome docs](https://developer.chrome.com/docs/extensions/reference/api/debugger)). WorkIt's extension does not request it and should keep it that way.

SmartRecruiters' side: DataDome's case study says SmartRecruiters deployed Bot Protect through its Cloudflare integration on "registration and application flows" to stop "automated submissions generated by bots and scripts". It allowlists customers who "use automation to submit applications legitimately" by "ASN or request patterns" ([case study, 2026-02-10](https://securityboulevard.com/2026/02/smartrecruiters-crushes-spam-job-applications-without-disrupting-real-users/)). The application form is exactly the endpoint being guarded.

## 4. What stays within the rules

**Legitimate:**
1. **The WorkIt extension in the user's everyday Chrome.** The user opens the posting, the extension fills it, and the user answers any challenge and presses Submit. This is how Simplify and Jobright work. SmartRecruiters' [terms of use](https://www.smartrecruiters.com/legal/terms-of-use/) (last modified 2019-05-14) bar "automatic means to access content or data from other users", harvesting, and overburdening servers. Filling your own application in your own browser touches none of these.
2. **Apply hands the posting to that path.** On a DataDome page (`ct.captcha-delivery.com` scripts or a `datadome` cookie, per the [JS tag docs](https://docs.datadome.co/docs/javascript-tag)), Apply closes its Worker page, marks a Handoff ("bot protection"), and opens the URL in the user's normal Chrome via `open -a "Google Chrome"`. It must not attach to that Chrome over CDP, or the same signals come back. The Handoff should not be retried automatically: DataDome's guidance for blocked agents is "Do not retry automatically" ([Agent Blocked](https://docs.datadome.co/docs/error-agent-blocked)), and retries can hurt the shared network's IP reputation.
3. **Official channels, mostly out of reach.** SmartRecruiters' [Application API](https://developers.smartrecruiters.com/docs/application-api) lets customers and partners create applications with keys from SmartRecruiters ([Get Started](https://developers.smartrecruiters.com/docs/get-started)). DataDome lets bots identify themselves with a dedicated user agent plus Web Bot Auth, reverse DNS or a static IP, but "our customers can decide to authorize them" ([Bot Authentication](https://docs.datadome.co/docs/bot-authentication); [Agentic Trust](https://docs.datadome.co/docs/agentic-trust-getting-started)). Both are for companies, not one applicant's agent.

**Not within the rules (note only):** engine patches or stealth drivers (invisible_playwright, undetected-chromedriver, Runtime.enable patches), spoofed fingerprints, rotating residential proxies, and captcha-solving services. Each exists to defeat a control the site put on its application form on purpose. That conflicts with SmartRecruiters' anti-overburden clause and the intent of its bot protection, and it risks blocks for a whole shared IP range. Even Simplify's own [terms](https://simplify.jobs/terms) (2026-08-19) treat "Circumvent, disable, defeat, avoid ... any authentication requirement" and rotating "proxies, or IP addresses" as prohibited on its site, which shows where the industry draws the line.
